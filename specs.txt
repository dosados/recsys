Задача.
Реализовать end-to-end рекомендательную систему.

Уточнения ТЗ (зафиксировано по итогам обсуждения):

1) Цель и рамки MVP
- цель MVP: рабочий pipeline с расчетом метрик;
- детали реализации отдельных метрик и точной логики ядер будут уточняться позже;
- критерий готовности: код + метрики + документация + тесты;
- в текущем этапе приоритет на сервисные слои, вызываемые из CLI; app-обертку пока игнорируем.
- во время длительных этапов обучения/обработки должны отображаться progress bars;
- по завершении каждого этапа должны писаться понятные логи о завершении (этап, статус, базовая сводка).

2) Фазы реализации ядер
- phase 1: GCN (LightGCN + MLP mapping);
- phase 2: остальные ядра (EMA, online k-means, two-tower) в произвольном порядке;
- команды для ядер должны быть унифицированы по интерфейсу (единая CLI-семья команд), но запускаться отдельно для каждого ядра;
- единой команды для одновременного прогона всех ядер быть не должно;
- сравнение ядер делается через несколько отдельных запусков CLI (по одному на ядро) с последующим сравнением сохраненных метрик.

3) Данные и протокол валидации
- используем VK-LSVD;
- temporal split: train week_00..24, validation week_25, test week_26;
- temporal-валидация без leakage обязательна;
- после MVP допускается отдельный режим обучения на расширенном множестве (в т.ч. train+val);
- пока используем существующие рабочие метрики на тех же данных, с вниманием к корректности/устойчивости расчета.

4) Политика сигналов (текущая)
- позитив: если есть хотя бы одно из like/share/bookmark/click_on_author/open_comments/timespent>30;
- сильный негатив: dislike;
- слабый негатив: timespent < 1;
- нейтральное: остальные просмотренные взаимодействия;
- при нехватке объектов для обучения допускаются случайные негативы из невзаимодействованных.

5) Ядра: ограничения на текущий этап
- EMA:
  - без user-level коррекций;
  - без временного затухания (старые взаимодействия весят так же);
  - без обязательного исключения уже просмотренных объектов из выдачи;
  - без требования resume с середины обучения.
- online k-means:
  - число центров k задается параметром (дальше подбирается экспериментально);
  - инициализация центров на усмотрение реализации;
  - каждый центр отражает отдельную группу интересов пользователя;
  - при рекомендации учитывать сходство со всеми центрами пользователя;
  - поддержка дрейфа интересов нужна.
- GCN (phase 1):
  - loss: BPR;
  - одна общая MLP-голова для маппинга в контентное пространство;
  - MLP обучается на item-эмбеддингах;
  - при инференсе тот же MLP применяется к user-эмбеддингам;
  - обучение этапное (не joint end-to-end на данном этапе).
- two-tower:
  - использовать все доступные user metadata;
  - использовать все доступные item metadata + content embeddings;
  - последовательные user history features в MVP не обязательны;
  - loss: BPR;
  - финальную формулу скоринга уточним позже.

6) Retrieval и вычисления
- обязательны 4 режима retrieval:
  - полный перебор;
  - полный перебор подмножества;
  - ANN перебор;
  - ANN перебор подмножества;
- для MVP подмножество можно формировать случайно;
- интерфейс retrieval должен быть единым для всех ядер;
- целевые режимы по памяти: около 10 GB и около 30 GB RAM.

7) Конфиги, артефакты, трекинг
- формат конфигов: JSON;
- строгая воспроизводимость (fixed seed policy) пока не обязательна;
- MLflow/W&B пока не подключаем;
- ключевой обязательный output текущего этапа: метрики (без обязательного model registry/сложных артефактов);
- resume длинных запусков пока не обязателен.
- после каждого запуска ядра метрики должны сохраняться на диск в стандартизованном формате.

8) Тестирование
- минимальный набор: unit + smoke;
- smoke-тесты нужны для каждого ядра;
- отдельные schema-contract тесты не обязательны на текущем этапе.

9) Архитектурные решения (дозафиксировано)
- главной единственной KPI-метрики нет: сравнение ядер выполняется по всему набору метрик;
- двухэтапный контур retrieval->rerank в MVP не требуется (только retrieval);
- граница ответственности:
  - core обучает модель представлений и возвращает user embeddings;
  - core может сохранить user embeddings на диск и возвращает статус готовности/путь до артефактов;
  - retrieval получает user embeddings и строит top-k кандидатов (строгий отдельный ранкер не обязателен);
  - eval считает метрики по результатам retrieval;
- основной ANN backend для MVP: FAISS;
- формат сервисов: Python-методы/классы внутри репозитория, вызываемые через CLI;
- для GCN phase 1 используем только user-item граф (без расширенного графового контракта).

ml cores - ядра для рекомендаций.
должен сопоставить соответствие пользователям их эмбеддингов в пространстве
контентных эмбеддитнгов предметов для поиска предметов для рекомендаций.


1)ema:
проходит по всем взаимодействиям пользователей и обновляет их эмбеддинги как ema эмбеддингов их позитивных взаимодействий.

2)online k-means:
как ema, но кластеризация позитивов с online k means а не единественный центр в ema


3)GCN:
строит граф взаимодействий и создает эмбеддинги с помощью litgGCN архитектуры, инициализируя из случайно. 
После этого эмбеддинги пользователей и предметов в новом латентном пространстве с помощью млп мапятся в промтранство
контентных эмбеддингов предметов. 
Обучается млп на предметах (тк есть эмбеддинги предметов как в пространстве взаимодействий так и в контентном)
после чего при предсказаниях мпл применяется к эмбеддингам пользователей в пространстве взаимодействий для получения
их в пространстве контента.
mlp и lightgcn реализованы с pytorch. система должна уметь работать батчево не перегружая память во время долгой 
работы над большим файлом.

4)two-tower:
первая башня пользователей - по метаданным
вторая башня предметов - поконтекнтным эмбеддингам + метаданным.
позитивный скор  сичтается успешным, обычное взаимодействие слабо успешным, негативное неуспешным, случайные среди
